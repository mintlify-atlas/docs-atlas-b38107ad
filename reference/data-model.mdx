All Allipos data lives in the browser's LocalStorage under two keys. No server, no database, no network calls — every product, every sale, and every session is stored entirely on-device and survives page refreshes, PWA restarts, and offline use.

## LocalStorage Keys

| Key | Contents |
|---|---|
| `allipos_products` | JSON array of Product objects |
| `allipos_sales` | JSON object with `totalSales` and `history` array |
| `allipos_catalog_version` | String version identifier used for auto-migration |

---

## Product Schema

Each item in the `allipos_products` array conforms to this shape:

<ResponseField name="id" type="string" required>
  Unique identifier for the product. Default catalog items use sequential IDs (`prod_1` through `prod_11`). User-created products use the format `prod_<timestamp>` where `<timestamp>` is the result of `Date.now()` at creation time (e.g. `prod_1728234567890`).
</ResponseField>

<ResponseField name="name" type="string" required>
  Display name shown on the product card in the POS view and in the sales history. Free-form text, entered by the store admin.
</ResponseField>

<ResponseField name="price" type="number" required>
  Unit price in Mexican pesos (MXN), stored as a floating-point number (e.g. `18.00`, `10.50`). Always parsed with `parseFloat()` before storage to normalize string input from the admin form.
</ResponseField>

<ResponseField name="image" type="string" required>
  Image source for the product card. Two formats are used:
  - **Bundled asset URL** — a hashed path like `/assets/prod_001-abc123.jpeg` generated by Vite at build time for the 10 default catalog products.
  - **Base64 data URI** — a `data:image/…;base64,…` string created by `FileReader` when a user uploads a custom photo from their camera or gallery.
</ResponseField>

```json
{
  "id": "prod_1",
  "name": "Gelatinas",
  "price": 18.00,
  "image": "/assets/inventory/prod_001-abc123.jpeg"
}
```

```json
{
  "id": "prod_1728234567890",
  "name": "Paletas de Hielo",
  "price": 12.00,
  "image": "data:image/jpeg;base64,/9j/4AAQSkZJRgABAQAA..."
}
```

## Sale Schema

Each element inside `allipos_sales.history` is a Sale object:

<ResponseField name="id" type="string" required>
  Unique identifier for the transaction, formatted as `sale_<timestamp>` where `<timestamp>` is `Date.now()` at the moment `Store.addSale()` is called (e.g. `sale_1728234590123`).
</ResponseField>

<ResponseField name="timestamp" type="string" required>
  ISO 8601 UTC timestamp of when the sale was recorded, generated via `new Date().toISOString()` (e.g. `"2026-10-06T15:23:10.000Z"`).
</ResponseField>

<ResponseField name="productId" type="string" required>
  References the `id` of the product sold. Note: products can be deleted after a sale is recorded, so do not assume the product still exists in `allipos_products`.
</ResponseField>

<ResponseField name="productName" type="string" required>
  Denormalized copy of the product name **at the time of sale**. Stored explicitly so the sales history remains accurate even if the product is later renamed or deleted.
</ResponseField>

<ResponseField name="quantity" type="number" required>
  Integer number of units sold in this transaction (e.g. `2`).
</ResponseField>

<ResponseField name="totalPayable" type="number" required>
  Total amount owed by the customer: `quantity × price` (e.g. `36.00` for 2 × $18). Stored as a float.
</ResponseField>

<ResponseField name="amountPaid" type="number" required>
  Cash amount tendered by the customer (e.g. `50.00`). Built up by tapping denomination buttons in Step 3 of the POS flow.
</ResponseField>

<ResponseField name="changeReturned" type="number" required>
  Change to return to the customer: `amountPaid − totalPayable` (e.g. `14.00`). Zero when the customer pays the exact amount.
</ResponseField>

The entire `allipos_sales` value stored in LocalStorage — the **sales store** — is a JSON object that wraps the history array with a running total:

```json
{
  "totalSales": 150.00,
  "history": [
    {
      "id": "sale_1728234590123",
      "timestamp": "2026-10-06T15:23:10.000Z",
      "productId": "prod_1",
      "productName": "Gelatinas",
      "quantity": 2,
      "totalPayable": 36.00,
      "amountPaid": 50.00,
      "changeReturned": 14.00
    },
    {
      "id": "sale_1728234510099",
      "timestamp": "2026-10-06T15:21:50.000Z",
      "productId": "prod_9",
      "productName": "Cakes Pops",
      "quantity": 3,
      "totalPayable": 75.00,
      "amountPaid": 100.00,
      "changeReturned": 25.00
    }
  ]
}
```

New sales are prepended to `history` (newest first) using `Array.unshift()`. `totalSales` is updated in the same write using `parseFloat((totalSales + newSale.totalPayable).toFixed(2))` to avoid floating-point drift.

## Catalog Versioning

The constant `CURRENT_CATALOG_VERSION` in `store.js` controls automatic migration of the product catalog:

```js
const CURRENT_CATALOG_VERSION = '2026.10.06.allipos_v1';
```

On every call to `Store.init()`, the saved version in `allipos_catalog_version` is compared against `CURRENT_CATALOG_VERSION`. A full re-seed from `INITIAL_PRODUCTS` is triggered if **any** of the following conditions are true:

1. `allipos_products` does not exist yet (first launch).
2. The stored catalog version string does not match the code's `CURRENT_CATALOG_VERSION`.
3. Any stored product image is a `data:image/svg+xml` URI — a legacy placeholder format used in earlier versions of the app.

This means catalog migrations are **automatic and invisible to the user**: they simply open the app and the updated product list appears.

<Tip>
  To force a catalog reset across all browsers, increment `CURRENT_CATALOG_VERSION` in `store.js` (e.g. change it to `'2026.10.06.allipos_v2'`). Every browser that loads the updated build will auto-migrate `allipos_products` to the new `INITIAL_PRODUCTS` on the next call to `Store.init()`.
</Tip>
